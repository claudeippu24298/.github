<h2>二、绑定参数：账号与出口的映射关系</h2>
<p>绑定是规划的地基。绑定关系不确定，主备切换就失去意义——切过去之后账号的出口变了，稳定性提升被关联风险抵消。</p>
<h3>绑定要写到「不可变」的层级</h3>
<p>建议绑定到「账号 ID → 出口 IP → 段 → 城市」四级，其中账号 ID 到出口 IP 是一对一，出口 IP 到段和城市是多对一。这样即使IP被回收，也能查到这个账号原本属于哪个段，避免新IP和旧账号落在同段。</p>
<h3>绑定的三种例外</h3>
<p>一是账号注销后的IP要空置至少 7 天才能重新分配；二是同一支付主体的账号不得共段；三是跨城市迁移要留档，写清迁移原因和时间，方便后续核对登录地记录。</p>
<h2>三、切换参数：主备判据与切换时机</h2>
<p>切换不是越灵敏越好。判据太灵敏，网络抖一下切一次，账号登录地记录全是乱的；太迟钝，故障持续几十分钟才发现。</p>

<h2>四、收敛参数：切换后多久恢复业务</h2>
<h3>按影响面决定切换范围</h3>
<p>收敛时间由四段组成：探测判定、切换执行、会话重建、业务重试。多数人只算前两段，实际占用最多的是后两段。切换范围也要跟着影响面走，能只切一条出口就不要整组切。</p>
<h3>把四段分别压下来</h3>
<p>探测判定通常 90 秒（3 次 × 30 秒），可以通过缩短间隔到 15 秒压到 45 秒，但会增加探测流量。切换执行取决于方式，DNS 方式受 TTL 影响，建议 TTL 设 60 秒；代理层切换通常秒级。会话重建要看客户端是否复用连接池，建议切换后主动清空连接池。业务重试就是前面说的指数退避。</p>
<p>四段加起来，理想情况 60 至 90 秒，现实常在 3 分钟以上。规划时按 3 分钟写进 SLA，别按 90 秒写。</p>

<h2>五、容量参数：并发与备用比例</h2>
<p>容量上限不要用标称值，用实测值的 60%。实测方法在上一节说过，用 hey 压到失败率 1% 时的并发数，再打六折。留 40% 余量是为了应对突发和探测流量。</p>
<p>备用比例 15%-20% 是经验值。低于 15%，一次批量故障就没有可换的资源；高于 25%，闲置成本明显上升。备用线路要保持在线预热，每 5 分钟探测一次，别等用时才开机。</p>
<h2>六、参数之间的约束关系</h2>
<p>最容易出错的是这三条联动：检查间隔 × 失败阈值 = 故障感知延迟；收敛时间 × 账号数 = 一次切换的业务影响面；备用比例 × 出口单价 = 每月固定冗余成本。三者互相牵制，改一个要重算另外两个。</p>
<p>举个例子：把失败阈值从 3 降到 2，感知延迟从 90 秒降到 60 秒，但误判率上升，切换次数增加，账号登录地记录变得更不稳定。这个代价往往比多等 30 秒大。所以阈值不建议低于 3。</p>
<p>再比如把收敛时间从 3 分钟压到 1 分钟，需要客户端支持快速重连，改造成本可能高于收益。先算清楚业务在 2 分钟中断里损失多少，再决定要不要投这笔改造。</p>
<h2>常见问答</h2>
<h3>主备切换会不会导致账号被要求重新验证？</h3>
<p>答：有可能。切换意味着出口变化，登录地记录会更新。降低影响的办法是让备用出口与原出口同城同段，把变化幅度降到最小，而不是完全不切。</p>
<h3>健康检查间隔设多少合适？</h3>
<p>答：30 秒是通用值。间隔太短会增加探测流量和误判，太长会拉长感知延迟。如果业务对中断极敏感，可以设 15 秒，但要把失败阈值同步调高到 4 次。</p>
<h3>回切要不要自动做？</h3>
<p>答：建议延迟回切。主线路恢复后先观察 30 分钟，确认稳定再切回，避免来回震荡。频繁在两个出口之间跳，对账号的登录记录最不友好。</p>
<h3>备用线路可以平时也跑业务吗？</h3>
<p>答：不建议跑正式业务，但建议跑探测和少量测试流量。完全不用的备用线路，真到切换时可能才发现配置早就失效了。</p>
<h2>合规提示</h2>
<p>本文的参数规划方法用于企业自有网络架构的稳定性设计与运维管理，目的是提升可追溯性和可用性，不应用于规避平台管理或伪造访问来源。</p>
<p>线路规划涉及账号与人员的映射信息，属于内部敏感数据，应设置访问权限、定期审计并遵守个人信息保护的相关要求。</p>
<p>文中取值为通用经验值，仅供参考，实际配置需结合设备能力、业务重要性与服务商条款确定，并在变更前做好回滚预案。</p>
